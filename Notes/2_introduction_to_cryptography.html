01 What Is Cryptography?

The art of secret writing

The word literally comes from Greek: krypto (hidden) + graphe (writing). The slide definition is worth memorizing word-for-word because professors love quoting it back at you:

Definition: "The art of mangling information into apparent unintelligibility in a manner allowing a secret method of unmangling."
plaintext
→ encryption →
ciphertext
→ decryption →
plaintext

The vocabulary you must know cold

  • Messages: plaintext (readable) and ciphertext (mangled)
  • Ingredients: an algorithm (the recipe/method) and one or more keys (the secret value(s) plugged into the recipe)
  • Players: the cryptographer invents clever algorithms; the cryptanalyst tries to break them
Think of it like a locked box: the algorithm is the design of the lock (everyone can see how the lock mechanism works), and the key is the one physical piece that actually opens it. Knowing how locks work in general doesn't let you open any specific one.
Public algorithm, secret key — this is the whole point: It's perfectly fine — even expected — for the algorithm itself to be public. What must stay secret is the key. "Sunlight is the best disinfectant": public algorithms get scrutinized by thousands of smart people, so weaknesses get found and fixed. A secret, untested algorithm just hides its flaws instead of removing them. An algorithm without the key does nothing to help unmangle the information.

02 Breaking an Encryption Scheme

How attackers actually attack, and why bigger keys matter

The slides describe three attack scenarios, ranked by how much the attacker has to work with:

Attack type What the attacker has What they do with it
Ciphertext only Just the scrambled message Try every possible key, check which result is actually intelligible English (needs a long enough sample to tell gibberish from a real sentence)
Known plaintext One or more (plaintext, ciphertext) pairs Work backward to figure out the key or algorithm pattern
Chosen plaintext The ability to get any plaintext encrypted on demand Feed in careful test messages and compare the ciphertext output to hunt for the key
Exam trap: These three are ordered from hardest for the attacker (ciphertext only) to easiest (chosen plaintext) — more access to the system always makes cryptanalysis easier, never harder.

Computational issues — why key/combination size matters so much:

The slides use a padlock as an approachable stand-in for a brute-force attack: try every possible combination until one works.

The combination lock math

  • 3-number combination, numbers 1–40 → 40³ = 64,000 possible combinations
  • At 10 seconds per attempt → 178 hours total (average case: half that, ≈ 89 hours)
  • Bump it to a 4-number combination (still 1–40, slightly slower to try at 13 sec/attempt) → 40⁴ = 2,560,000 combinations → 9,244 hours
The lesson: adding just one more digit to the combination didn't make it 40 times harder to crack in a linear sense — it multiplied the total search space by 40, and the time to crack it grew right along with it. This is exactly why adding a few extra bits to an encryption key can turn "crackable in an afternoon" into "crackable in longer than the age of the universe."
Fundamental Tenet of Cryptography (from the slides): "If lots of smart people have failed to solve a problem, then it probably won't be solved (soon)." This is why algorithms that have survived years of public attack (like AES) are trusted more than something brand new and unreviewed.

03 Types of Cryptographic Functions

The three big families — everything else is a variation on these

Type Keys involved Also called
Public Key Two keys: public + private Asymmetric cryptography
Symmetric Key One key, shared between both sides Secret key / conventional cryptography
Hash Functions No keys at all (or an optional key for a "keyed hash") Message digest functions
Quick way to tell them apart on an exam question: If the question mentions decrypting something back to the original, it's symmetric or public key. If it only ever goes one direction (message → fixed-size fingerprint, no way back), it's a hash.

04 Secret Key (Symmetric) Cryptography

One shared secret, known to both sides

plaintext
→ encrypt (key K) →
ciphertext
→ decrypt (same key K) →
plaintext

The same key K both locks and unlocks the message — which is exactly why it must be shared secretly beforehand, and why it's also called "conventional" cryptography (it's the oldest, most intuitive kind).

What symmetric keys are used for

  • Transmission over an insecure channel — sender and receiver share a secret in advance, so eavesdroppers on the wire see only ciphertext
  • Secure storage on insecure media — encrypt data before saving it somewhere untrusted (a shared drive, cloud storage, a stolen laptop's disk)
  • Authentication — specifically strong authentication: proving you know the secret key without ever revealing the key itself

Worked example — challenge/response authentication:

Alice and Bob both secretly know KAB = +3 (a Caesar shift). To prove to each other they both know the key without ever saying it out loud:

  • Alice sends Bob a random challenge, rA = "marco"
  • Bob encrypts it with the shared key and sends it back: "marco" shifted +3 → "pdufr"
  • Bob sends his own random challenge back, rB = "polo"
  • Alice encrypts that with the same key: "polo" shifted +3 → "sror"
  • Each side checks the other's response matches what they'd expect — proving both know KAB without ever transmitting it directly
    • Why the challenge is random each time: If Alice just asked "encrypt the word PASSWORD," an eavesdropper who recorded the reply once could replay it forever. A fresh random challenge every single time means a recorded old answer is useless — this is what "strong authentication" buys you over just checking a static password.

    05 Classical Ciphers & Frequency Analysis

    Secret key crypto's simplest ancestors — and why they fall apart

    Cipher How it works Example
    Caesar cipher Shift every letter a fixed number of places forward Shift by 3: DOZEN → GRCHQ
    "Secret decoder ring" Same idea, but the shift amount n can be 1–25 instead of always 3 Shift by 1: HAL → IBM
    Monoalphabetic cipher Any arbitrary letter-for-letter mapping, not just a simple shift 26! ≈ 4.03 × 10²⁶ possible mappings
    Polyalphabetic cipher (e.g. Vigenère) The same plaintext letter can map to different ciphertext letters depending on position, using a repeating keyword Plaintext GEEKS + key FIRST → different letters, shifted by a different amount each position
    The huge key space trap: 26! looks unbreakable — at 1 millisecond per guess, brute-forcing every mapping would take about 10 million years. So why is monoalphabetic substitution actually weak? Because you don't need to brute-force the key at all — you can use letter frequency analysis instead.
    Frequency analysis, explained simply: In normal English text, "E" shows up about 12.7% of the time, "T" about 9%, while "Z" and "Q" barely appear at all. If a monoalphabetic-enciphered message has one symbol appearing constantly, it's very likely standing in for "E." You don't crack the whole key at once — you guess letter by letter based on how common each symbol is, then use context to fill in gaps. It turns an astronomical brute-force problem into an educated-guessing problem.

    Why polyalphabetic (Vigenère) ciphers resist frequency analysis better

    • Because one plaintext letter can turn into several different ciphertext letters depending on where it sits in the message, the neat one-symbol-equals-one-letter frequency pattern gets smeared out
    • This is exactly the question the slides pose: "Can frequency analysis work here?" — the honest exam answer is: not directly, it's much harder, though patterns can still leak if the keyword repeats and the message is long enough (a fact worth mentioning if the exam asks you to elaborate)

    06 Public Key Cryptography

    Two keys instead of one — no secret needs to be shared in advance

    plaintext
    → encrypt (public key) →
    ciphertext
    → decrypt (private key) →
    plaintext

    The two keys, and how they differ from "secret key"

    • Public key: published, ideally known as widely as possible — anyone can use it to encrypt a message to you
    • Private key: kept by you alone, never published — note the slides are careful to call it "private key," not "secret key," to avoid confusing it with symmetric crypto's shared secret
    Think of it as a mailbox with a slot: anyone (Bob) can drop a letter through the public slot (encrypt with Alice's public key), but only Alice, who holds the one physical key to the box (private key), can open it and read what's inside.
    Efficiency problem — very testable: Public key algorithms are orders of magnitude slower than symmetric key algorithms. Nobody encrypts a whole large file or video stream with pure public key crypto — it's used briefly to set things up, then handed off.

    The hybrid model (the practical fix for that slowness):

  • Use public key crypto just once, briefly, to establish a temporary shared symmetric key
  • Switch to that fast symmetric key for the rest of the actual communication

    • Secure storage on insecure media — two documented options:

    Option How it works
    Option 1 Encrypt the data directly with the public key; decrypt later with the private key
    Option 2 (the hybrid approach) Generate a random symmetric secret key, encrypt the actual data with that (fast), then encrypt just the small secret key itself with the public key
    Why Option 2 usually wins in practice: You get the speed of symmetric encryption for the (potentially large) data, and public key crypto only has to do its slow work on one tiny key instead of the whole file.

    07 Hash Algorithms

    Message digests — one-way, no key required

    A hash function takes a message of any length and produces a fixed-size fingerprint (the digest). It's designed to be a one-way street — you can go from message to digest easily, but never back the other way.

    The four required properties (memorize these)

    • Easy to compute the hash for any given message
    • Infeasible to find a message that produces a given hash (one-wayness / preimage resistance)
    • Infeasible to modify a message without changing its hash
    • Infeasible to find two different messages with the same hash (collision resistance)
    The slide's own demo makes the point well: changing just one letter in "The red fox jumps over the blue dog" (e.g. swapping two letters in "over") produces a completely different, unrelated-looking digest each time — there's no partial credit. A tiny change in the input scrambles the whole output ("avalanche effect").
    Hash lifecycle — algorithms get retired: The slides show a "breakout chart" where older hash functions (Snefru, MD4, MD5, SHA-0) turn red over time as collisions or weaknesses were found in them. The exam-relevant point: no hash algorithm is safe forever — what's considered secure shifts as cryptanalysis improves, which is why MD5 is now considered broken for security purposes even though it's still used for basic (non-adversarial) integrity checks.

    Password hashing:

    How it's supposed to work

    • Systems store only the hash of your password, never the password itself
    • At login, your typed password is hashed again and compared to the stored hash
    • Even so, passwords can still be guessed via dictionary attacks — hashing protects against reversing the hash, not against someone hashing common passwords and comparing results (which is exactly what happened in the LinkedIn breach referenced in the slides)

    Message integrity — the keyed hash:

    Alice and Bob share a secret. Alice hashes (message + secret) together and sends both the message and that hash. Bob recomputes the same hash using the message he received plus the shared secret, and checks whether it matches.

    Why this proves integrity: If anyone tampered with the message in transit, Bob's recomputed hash won't match the one Alice sent — and an attacker can't forge a matching hash without knowing the shared secret.

    Digital signatures — hashing meets public key crypto:

    plaintext
    → sign (private key) →
    signed message
    → verify (public key) →
    plaintext

    Two properties this asymmetry buys you

    • A signature can only be generated by whoever holds the private key
    • A signature can be verified by absolutely anyone, using the public key
    • Non-repudiation: the sender can't credibly claim they never sent it — the flip side/caveat is that this only holds if the private key itself was never stolen

    One-Page Recap

    • Cryptography: mangling information (plaintext → ciphertext) in a way that allows secret unmangling. Public algorithm, secret key — never the reverse.
    • Breaking a scheme: ciphertext-only (hardest for attacker) → known-plaintext → chosen-plaintext (easiest). Bigger key/combination space grows crack-time exponentially, not linearly.
    • Three function families: public key (two keys), symmetric key (one shared key), hash functions (no key, one-way).
    • Symmetric key: same key encrypts and decrypts; used for insecure-channel transmission, insecure-media storage, and challenge–response authentication (never send the key itself).
    • Classical ciphers: Caesar/monoalphabetic ciphers fall to frequency analysis even with a huge key space; polyalphabetic (Vigenère) resists this better by varying the mapping per position.
    • Public key: public key encrypts, private key decrypts. Much slower than symmetric — real systems use a hybrid model (public key sets up a fast symmetric session key).
    • Hash functions: one-way fingerprints. Used for password storage (still guessable via dictionary attack), keyed-hash message integrity, and — combined with private-key signing — digital signatures with non-repudiation.

    Q: Is it a problem if the encryption algorithm itself is public?

    A: No — it's actually preferred ("sunlight is the best disinfectant"). Only the key must stay secret.

    Q: Rank the three attack types from hardest to easiest for the attacker.

    A: Ciphertext-only (hardest) → known-plaintext → chosen-plaintext (easiest).

    Q: Why does frequency analysis break a monoalphabetic cipher despite 26! possible keys?

    A: Because it doesn't need to search the key space at all — it exploits how often each letter naturally occurs in English to guess the mapping directly.

    Q: Why is public key crypto usually paired with a symmetric key in real systems?

    A: Public key algorithms are far slower; the hybrid model uses public key crypto only to set up a fast shared symmetric key for the rest of the session.

    Q: What's the difference between a digital signature's "verify" step and message-integrity's keyed hash?

    A: A keyed hash needs both sides to already share a secret. A digital signature uses asymmetric keys, so anyone can verify it with the signer's public key — and it adds non-repudiation.

    Q: Does hashing a password make it unguessable?

    A: No — it prevents reversing the hash back to the password, but dictionary/guessing attacks can still succeed by hashing common passwords and comparing.

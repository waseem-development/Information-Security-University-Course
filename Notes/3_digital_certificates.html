01 The Core Problem: Public Key Deception

Why we need any of this in the first place

Public key encryption is great: everyone has a public key (shareable) and a private key (secret). The catch is trust — how do you know the public key you received actually belongs to the person you think it does?

Think of it like this: Someone calls you pretending to be your bank and gives you a "callback number" — but it's actually their own number, not the bank's. If you call it back to "verify," you're really just talking to the impostor again. The number itself proved nothing, because it came from the same untrusted source.

What the impostor gains

  • Pass any public-key authentication check (their private key matches the "public key" you accepted)
  • Decrypt any messages the verifier encrypts and sends back, since they were encrypted with the impostor's public key
The moral (this is basically the whole point of the topic): Public key crypto only works for privacy, authentication, and integrity if the verifier gets the true party's public key independently — from a trusted third party, not from the applicant itself.

02 Digital Certificates

The fix for public key deception

A digital certificate is basically an ID card for a public key. It's a small file that says:

"I, the Certificate Authority, have checked that this name owns this public key. Signed, sealed, dated."

What's inside / what it does

  • Binds a name to a public key (a name–public key pair)
  • This binding is what prevents public key deception — the key doesn't come from the applicant, it comes bundled with a third party's stamp of approval
  • The format/fields are standardized by the ITU-T X.509 standard (so every system reads certificates the same way)
  • The whole certificate is digitally signed using the CA's own private key — this is what makes it tamper-proof: if an impostor edited the name field, the signature would no longer match, and the forgery would be obvious
Common exam trap: "A digital certificate alone provides authentication." — FALSE. A certificate only proves who owns a public key. On its own it does NOT check whether that certificate has since been revoked. You still need a CRL check (next section) for real authentication.

Important caveats

  • CAs are not regulated — anyone could technically set one up
  • So you must only trust CAs you actually trust (browsers/OSs ship with a pre-approved trusted CA list)
  • A company can be its own CA just for internal use — e.g. issuing certificates to its own employees, servers, and devices

04 Revocation & the CRL

What happens when a certificate goes bad early

Certificates have an expiration date, but sometimes a CA needs to kill one before that date — e.g. an employee leaves the company, or a private key gets stolen/compromised.

  • The CA puts the certificate's ID number on its Certificate Revocation List (CRL)
  • Anytime a verifier receives a digital certificate, it must ask the CA: "is this one on the CRL?"
  • The CA responds: OK or Revoked
    • Exam-critical line straight from the slides: "Without the CRL check, digital certificates do NOT support authentication." Memorize this — a certificate you never checked against the CRL could belong to someone who was fired/compromised yesterday.

    05 Public Key Infrastructure (PKI)

    The whole system running in the background

    A PKI is the full setup an organization builds to automate all of this — private key creation, certificate creation/distribution, and CRL checking. The engine behind it is usually called a PKI Server.

    Job of the PKI Server What it actually does
    Create key pairs Generates public/private key pairs for applicants
    Distribute private keys Sends the private key securely to the applicant — often it's simply embedded inside software delivered to them
    Distribute certificates Sends digital certificates to verifiers when needed
    CRL checking Checks the revocation list before confirming a certificate is valid, and answers "OK / Revoked" to verifiers
    Think of a PKI Server as the DMV of the digital world: it issues your "ID" (certificate), keeps a record of who it's given IDs to, and if your ID gets reported stolen, it can flag it as invalid the moment someone tries to check it.

    06 Integrated Security System (ISS)

    What actually happens when two computers talk securely

    This is the general 4-step "handshake" pattern almost every secure system follows (your browser and a bank website, two apps, etc.) — the software handles it automatically:

  • Negotiate — the two sides agree on which security methods/algorithms to use
  • Authenticate — they confirm each other's identity (using certificates, from Section 2–4!)
  • Exchange a session key — they agree on one shared symmetric key just for this session (symmetric = fast, good for bulk data — unlike public key crypto which is slower)
  • Communicate securely — every message after this point is encrypted + signed using that session key, giving privacy, authentication, and message integrity together
    • Why switch to a symmetric key at all if we already have public/private keys? Public key encryption is computationally expensive. Once identities are confirmed, it's much faster to use one shared symmetric key for the rest of the conversation.

    07 SSL / TLS — the real-world example of an ISS

    The thing your browser is doing right now

    Term Meaning
    SSL Secure Sockets Layer — originally built by Netscape
    TLS Transport Layer Security — the modern, IETF-controlled rename of SSL (people still just say "SSL" out of habit)

    Where it sits

    • Runs below the Application Layer (browser, e-mail, etc.) but above the Transport Layer
    • Not tied to one single app — it protects WWW traffic, e-mail, and more, all the same way

    SSL's version of the ISS handshake:

  • Browser and webserver negotiate security parameters
  • The webserver authenticates itself (using its certificate) — this is why you see the padlock icon
  • The browser can authenticate itself too, but in practice rarely does
  • Browser picks a symmetric session key and sends it to the webserver
  • From here on, everything is signed + encrypted with that symmetric key
    • Known weaknesses to remember for the exam:
    • Relatively weak security compared to newer schemes
    • Says nothing about whether the merchant's server itself is actually secure
    • Does NOT validate credit card numbers
    • Considered a "good enough for now" stopgap, not a permanent perfect solution

    SSL/TLS is just one example of an ISS. Others include IPsec, PPP, and PPTP — but every single one of them follows the same 4-step pattern from Section 6: negotiate → authenticate → exchange session key → communicate securely.

    One-Page Recap

    • Problem: An impostor can hand out their own public key while claiming it belongs to someone else (public key deception).
    • Fix #1 — Digital Certificate: A signed document binding a name to a public key, following the X.509 standard.
    • Fix #2 — Certificate Authority: The trusted third party that verifies identity and signs the certificate. Not regulated — only trust CAs you actually trust.
    • Fix #3 — CRL: A list of revoked certificates. Without checking it, a certificate proves nothing about current validity.
    • PKI: The whole automated system (PKI Server) that creates keys, issues certificates, and handles CRL checks.
    • ISS: The general handshake — negotiate → authenticate → exchange session key → communicate securely with a fast symmetric key.
    • SSL/TLS: The most common real-world ISS. Secures browser traffic (and more), but has known limits (doesn't secure the merchant's server or validate card numbers).

    Q: Does a digital certificate by itself authenticate someone?

    A: No — you also need to check the CRL to make sure it hasn't been revoked.

    Q: Why can't the applicant just hand their public key straight to the verifier?

    A: Because the verifier has no way to independently confirm it really belongs to that party — this is exactly the public key deception attack.

    Q: What does the CA sign the certificate with?

    A: Its own private key — that's the digital signature that gives the certificate message integrity.

    Q: In SSL, who usually authenticates — browser, server, or both?

    A: The webserver authenticates itself; the browser can, but rarely does in practice.

    Q: Why switch to a symmetric session key after authentication?

    A: Public key encryption is slow; a shared symmetric key is much faster for ongoing communication.
